# Android Platform Review

## 1. Summary

Platform correctness is fundamentally sound: every Compose state collection uses `collectAsStateWithLifecycle`, ViewModels confine work to `viewModelScope`, no `!!` operators appear in production sources, and the AccessibilityService scope is lifecycle-tied with `SupervisorJob + Dispatchers.IO`. The most consequential finding is the AccessibilityService's `onAccessibilityEvent` hot path: it mutates shared state (`currentTrackedPackage`, `currentSessionId`) on the event thread while concurrently writing the same fields from an IO coroutine, exposing a TOCTOU race and the possibility of orphaned `usage_sessions` rows. Several `LaunchedEffect(Unit)` blocks capture mutable state (notably the back-press dispatcher's reference to `viewModel.state.value` in `BlockOverlayActivity`) that is fine in practice but worth tightening. Manifest configuration matches the service code well, but the `QUERY_ALL_PACKAGES` permission is requested at top level without an Android 11+ justification comment, which is a Play Store flag. Onboarding state (current pager page) is not preserved across process death — a minor UX regression on low-memory devices.

## 2. Findings

### Compose state

- **[Medium]** `app/src/main/java/com/appblocker/presentation/screen/OnboardingScreen.kt:77` — `pagerState` uses `rememberPagerState` rather than a saveable variant. After process death the user returns to page 0 even after having scrolled to page 3. Wrap the page-index in `rememberSaveable` and seed `rememberPagerState(initialPage = saved)` so onboarding survives recreation.
- **[Medium]** `app/src/main/java/com/appblocker/presentation/screen/HomeScreen.kt:161` — `selected` (the focus duration `DurationChoice`) is held in plain `remember`. On rotation the user loses their picked duration and snaps back to 30 min. Promote to `rememberSaveable` with a custom `Saver`, or hoist to the ViewModel.
- **[Medium]** `app/src/main/java/com/appblocker/presentation/screen/MainScreen.kt:93-94` — `pickerApps` and `isPickerLoading` use `remember`. If a config change happens while the picker sheet is open (`showAppPicker` is correctly `rememberSaveable`), the sheet reopens empty and refetches. Hoist this list state to a ViewModel so the open sheet survives recreation.
- **[Low]** `app/src/main/java/com/appblocker/presentation/BlockOverlayActivity.kt:72` — `LaunchedEffect(Unit)` body captures `blockedPackage` (a `lateinit var` that never changes post-`onCreate`) and `viewModel` (stable). Acceptable today, but if `blockedPackage` ever becomes mutable this captures the original. Key the effect on `viewModel` for explicitness.
- **[Low]** `app/src/main/java/com/appblocker/presentation/screen/OnboardingScreen.kt:83` — `LaunchedEffect(Unit)` reads `pagerState.currentPage` via `snapshotFlow`. The effect itself is correct (Unit key is fine because `pagerState` is remembered), but the surrounding `LaunchedEffect(showHint)` at line 94 launches an unbounded `while (true)` loop whose cancellation depends solely on `showHint` flipping. If the page is restored to page 0 with `hasInteracted = true`, the loop never starts; if `showHint` flips during the inner `delay(1200)`, the cancellation is clean — but the relationship between the two effects is fragile and merits a comment.

### Coroutines

- **[High]** `app/src/main/java/com/appblocker/service/AppBlockerAccessibilityService.kt:62-75` — `endCurrentSession()` runs on the AccessibilityService event thread and reads/writes `currentTrackedPackage` / `currentSessionId`, while the `serviceScope.launch { ... }` block that *sets* those same fields runs on `Dispatchers.IO`. Two consecutive events for different packages can interleave: event A's coroutine writes `currentSessionId = X` after event B has already nulled it, leaving session X open in the DB forever. Either move all mutations into a single-threaded confinement (e.g. a `Channel<AccessibilityEvent>` consumed by one collector) or mark the fields `@Volatile` and use atomic compare-and-set; the current `private var` is not safe across threads.
- **[Medium]** `app/src/main/java/com/appblocker/presentation/MainViewModel.kt:72-78` — `startClockTick` runs `while (true) { delay(1_000) }` for the lifetime of the ViewModel, even when no UI subscribes (e.g. when only the Apps or Schedules tab is visible). Convert `now` to a `flow { while (true) { emit(...); delay(1_000) } }` shared via `stateIn(viewModelScope, SharingStarted.WhileSubscribed(5_000), ...)` so the tick stops when no Composable is collecting.
- **[Low]** `app/src/main/java/com/appblocker/service/AppBlockerAccessibilityService.kt:22` — `serviceScope` uses `Dispatchers.IO`. `onAccessibilityEvent` itself runs on the system event thread, so all coroutine work correctly dispatches off it. Acceptable, but if anything ever calls `serviceScope.launch(Dispatchers.Main)` for UI work the supervisor will still need a Main dispatcher; keep this in mind.

### AccessibilityService

- **[High]** `app/src/main/java/com/appblocker/service/AppBlockerAccessibilityService.kt:66-75` — Every non-ignored, non-grace `TYPE_WINDOW_STATE_CHANGED` event spawns a coroutine that hits Room (`isAppBlocked` → `isBlockingEnabled` + `getActiveSession` + `getActiveSchedulesForApp` + possibly `getTodayTotalDurationMs`). Window state events fire at a high rate during scrolling, multi-window activity, and IME transitions. There is no in-memory cache of "is this package blocked" and no debounce; under load the IO dispatcher can queue dozens of DB round-trips per second. Add a `StateFlow<Set<String>>` of blocked package names populated once at service start (and observed thereafter) so the hot path is an O(1) `Set.contains` check; only fall back to DB for the schedule/limit branch when a package is actually in the set.
- **[High]** `app/src/main/java/com/appblocker/service/AppBlockerAccessibilityService.kt:69-74` — Once an app is detected as blocked the service calls `launchBlockOverlay` on every event, including events fired by the overlay itself or by re-entries after the overlay finishes. The `currentTrackedPackage != packageName` guard prevents *some* duplication but does not prevent re-launching the overlay if the same blocked package fires another `TYPE_WINDOW_STATE_CHANGED` while the overlay is already on top. Add a short debounce (e.g. ignore the same package within 500 ms) or check that the overlay activity is not already in foreground before calling `startActivity`.
- **[Medium]** `app/src/main/java/com/appblocker/service/AppBlockerAccessibilityService.kt:78-92` — `launchBlockOverlay` calls `packageManager.getApplicationInfo` synchronously on the event thread. This is usually fast but is still IPC; move it inside the existing `serviceScope.launch` block or cache resolved app labels by package name.
- **[Medium]** `app/src/main/java/com/appblocker/service/AppBlockerAccessibilityService.kt:39-50` — `onCreate` instantiates three repository implementations and two use cases on the main thread. `AppDatabase.getInstance` is `synchronized` and lazy; the Room builder defers schema work to first query, so this is acceptable, but the manual wiring should ideally move to a DI container (Hilt/Koin) to avoid drift between `MainViewModel`, `BlockOverlayActivity`, and the service all building the same graph independently.

### Lifecycle / leaks

- **[High]** `app/src/main/java/com/appblocker/service/AppBlockerAccessibilityService.kt:120-128` — The companion object holds `graceUntilMs: ConcurrentHashMap<String, Long>` as static state, and `grantGrace` is called from `BlockOverlayActivity` (`BlockOverlayActivity.kt:78`). The map only holds package-name strings and longs, so there is no Context leak — but the grace window state outlives the service itself: if the user disables the Accessibility Service, the map persists in the process, and there is no eviction. Add a periodic prune (or compute-and-remove inside `isInGrace`, which is already done lazily — confirmed correct at line 97). The static map across Activity → Service is also brittle: if the Activity grants grace while the service is destroyed and the OS later starts a fresh process, the grace is lost. Persist grace expiries to SharedPreferences if cross-process-death survival matters.
- **[Low]** `app/src/main/java/com/appblocker/data/local/AppDatabase.kt:48-49` — `@Volatile private var INSTANCE: AppDatabase?` is the canonical double-checked-locking singleton; `Room.databaseBuilder` is called with `context.applicationContext`, so no Activity context leaks. No finding — included as a positive calibration point.

### Manifest

- **[High]** `app/src/main/AndroidManifest.xml:4` — `QUERY_ALL_PACKAGES` is declared at top level with no `tools:ignore` or comment explaining the Play Store policy justification. Google Play requires apps using this permission to fall under an approved use case (app blocker / parental controls qualifies, but the permission must be declared with an attached justification in the Play Console). Add a comment in the manifest pointing to that policy and confirm the Play Console declaration; otherwise consider switching to `<queries>` with intent filters for launcher activities, which `loadInstalledApps` already iterates (`MainScreen.kt:176-179`).
- **[Medium]** `app/src/main/AndroidManifest.xml:10`, `:29` — Activities and the application use `Theme.MaterialComponents.DayNight.*` themes. The app is otherwise pure Compose + Material 3; the legacy Material Components theme is unnecessary and pulls in AppCompat resources. Migrate to a Material 3 (`Theme.Material3.*`) base or a custom `Theme.AppBlocker` that extends a Material 3 theme.
- **[Medium]** `app/src/main/res/xml/accessibility_service_config.xml:4` — `android:accessibilityEventTypes="typeWindowStateChanged"` matches the code (`AppBlockerAccessibilityService.kt:54` only handles that one type) — good. However, `packageNames` is not set, so the service receives events for *every* package on the device. The service maintains its own ignore-list at `AppBlockerAccessibilityService.kt:29-35`, but filtering at the OS level is cheaper. Since the set of blocked packages is dynamic, an XML `packageNames` filter is impractical — instead, consider `setServiceInfo` at runtime to narrow event delivery to the actual blocked set, which would also reduce wakeups.
- **[Low]** `app/src/main/res/xml/accessibility_service_config.xml:8` — `notificationTimeout="100"` is reasonable for window-state debounce; no change suggested.
- **[Low]** `app/src/main/AndroidManifest.xml:7` — `android:allowBackup="true"` is the default. For a privacy-first app whose database contains usage and motivational data, consider `android:allowBackup="false"` or define `android:fullBackupContent` to exclude `app_blocker.db`.

### Nullability

- No findings. `grep '!!' app/src/main` returns zero hits in production code. Null handling is consistent throughout: `?:` defaults, `?.toString()`, `?.let { ... }`, sealed-state guards, and explicit early returns. This is a positive — call it out as the calibration low-bar.

## 3. Calibration examples

- **Critical**: none flagged. No data-loss bug or guaranteed crash was identified — the threading race in `AppBlockerAccessibilityService.kt:62-75` is rated High rather than Critical because the worst case is an orphan `usage_sessions` row, not a crash.
- **High** (3 examples used):
  - `AppBlockerAccessibilityService.kt:62-75` — cross-thread mutation of session-tracking state.
  - `AppBlockerAccessibilityService.kt:66-75` — synchronous DB on every window-state event.
  - `AndroidManifest.xml:4` — `QUERY_ALL_PACKAGES` without policy justification.
- **Medium** (4+ examples used): pager state not saveable (`OnboardingScreen.kt:77`); duration selection not saveable (`HomeScreen.kt:161`); legacy MaterialComponents theme (`AndroidManifest.xml:10`); never-ending `now` ticker (`MainViewModel.kt:72-78`).
- **Low** (3 examples used): `LaunchedEffect(Unit)` style (`BlockOverlayActivity.kt:72`); `allowBackup="true"` (`AndroidManifest.xml:7`); positive note on `@Volatile` singleton (`AppDatabase.kt:48`).

## 4. Not detailed

- `BlockOverlayViewModel.kt:38-52` — `countdownJob = viewModelScope.launch` is correct; the loop reads `_state.value` and bails out as soon as the state is no longer `BreathingPause`, so transitions via `onSkipBreath` or back-press cleanly terminate it.
- `BlockOverlayViewModel.kt:32-33` — `Channel<BlockOverlayEvent>(Channel.BUFFERED)` + `receiveAsFlow()` is the correct one-shot-event pattern; not a SharedFlow, which is right because we want at-most-once delivery, not replay.
- `MainActivity.kt:16-21` — SharedPreferences read happens synchronously on the main thread in `onCreate`. The `app_blocker_prefs` file is tiny and this is the standard Android pattern, but for cold start latency on slow devices consider DataStore.
- `OnboardingActivity.kt:20-23` — `prefs.edit().apply()` is async-safe; no finding.
- `MainScreen.kt:171-193` — `loadInstalledApps` runs inside `withContext(Dispatchers.IO)` — good.
- `MainScreen.kt:161-169` and `AppNavigation.kt:170-178` — duplicated `checkAccessibilityService` / `checkAccessibilityServiceStatus` implementations. Extract to a shared utility.
- `IsAppBlockedUseCase.kt:48-49` — `LocalTime.parse(it)` on every check; cached schedules avoid re-parsing if cached as `LocalTime` rather than `String`.
- `IsAppBlockedUseCase.kt:50` — `now in start..end` does not handle wrap-around windows (e.g. 22:00–06:00). If schedules ever span midnight this will silently never match.
- `AppDatabase.kt:51-110` — Migrations are reversible-aware and use `IF NOT EXISTS` / `IF EXISTS` correctly. Schemas are exported (`exportSchema = true`). Good.
- `ScheduleDao.kt:64-95` — `@Transaction` correctly wraps the multi-step insert/update of schedule + days + apps.
- `BlockOverlayViewModel.kt:118-128` — `ViewModelProvider.Factory` could be replaced with `viewModelFactory { initializer { ... } }` for less boilerplate but the current form is correct.
- `Theme/Color.kt`, `Theme/Type.kt`, `Theme/Theme.kt` — not reviewed in depth; assumed correct unless theme-setup flags otherwise.
- `MainScreen.kt:81-89` and `AppNavigation.kt:88-92` — both poll accessibility status via `repeatOnLifecycle(RESUMED)`. The Apps tab’s polling is redundant with the navigation host’s polling; the result is read into a local `var` in `MainScreen` but never propagated up. Consider a single accessibility-status `StateFlow` in a ViewModel.
- `BlockOverlayActivity.kt:54-57` — Calling `finish()` from `onCreate` then `return` is correct, but the subsequent code references `blockedPackage` (lateinit) which is safe because of the `return`. No finding.
- `BlockOverlayActivity.kt:61-64` — Back-press handler reads `viewModel.state.value` directly. This is fine because `OnBackPressedCallback#handleOnBackPressed` runs on the main thread; the StateFlow value read is a snapshot.
- `AccessibilityBanner` lives inside `MainScreen.kt` but is dismissed via SharedPreferences whose key (`"accessibility_prompt_dismissed"`) is read in the same lifecycle effect. The write at line 122 uses `.apply()` which is async — the next `repeatOnLifecycle(RESUMED)` pass will see the new value. Acceptable.
